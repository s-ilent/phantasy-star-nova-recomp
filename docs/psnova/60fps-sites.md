# 60 fps: how the game paces itself (agent research, 2026-11-19, each list checked by a second agent)

Raw findings from the workflow psnova-60fps-sites (read-only code reading, nothing run). Addresses are 1.05 NovaMRom.

## pacing

**Summary.** I re-checked every finding against the generated C (game_part12/35/47/49/50/51.c). I also read the ELF (vtable and data defaults) and runtime/gfx/display.c and runtime/core/hooks.c. Nothing in the project was changed.

The pacing core holds:
- The VSync thread counts vblanks.
- The vblank callback adds exactly 1 per call and ignores notifyCount.
- One frame limiter waits uidiv(60, singleton+0xcc) vblanks. It has exactly one call site, 0x81a775b6 in the per-frame task fn_81a7756c. I confirmed that vtable 0x8245c0a0 slot +0x34 holds 0x81a7756d.
- The only store of 30 is `movs r1,#0x1e` at 0x8178c5f2, followed by `str.w r1,[r0,#0xcc]` at 0x8178c5f4. It is in fn_8178c3e4, which runs once at startup, called from fn_81294662 at 0x81294664.

Corrections:
1. The limiter calls the renderer hook fn_81a72074 whenever two_phase is set. Only the early wait to target-1 depends on counter+1 < target, so at 60 fps that early wait never happens. The hook only posts command 0xa into the render thread's queue (fn_81a8ff10).
2. The 1/30 list was wrong in places:
   - 0x81365eb2 multiplies elapsed vblanks (singleton+0x8c) by 1/30. That is vblank-based, so it is not tied to fps.
   - 0x8186ee42, 0x8186f15c and 0x81fcc6bc (the movw; its movt is at 0x81fcc6c8) are a one-time conversion of four stored values (+0x50..+0x5c) into seconds, with a done flag at +0x6c. They do not run per frame.
   - 0x81ac2014 and 0x81ac2034 (a site the first report missed) cap a measured delta at 1/30. That has no effect at 60 fps.
   - 0x81294698 writes 1/30 into a 4-byte step object, *0x82494030, whose constructor default is 1/60 (0x81af5d42). I found no reader of that float.
   - The extra 1/31 movw/movt pairs in fn_81a095c0 and nearby are RGB565 colour decoding, not timing.
3. 0x82474334 matters more than the report said. Its default in the ELF data is 0.016 (0x3c83126f), and only the 30 fps init overwrites it with 1/31. fn_81ad46c4 (and probably fn_81ad4cb0 and fn_81ad4fdc) turns it into a count: int(dt/step) when step <= dt, otherwise int(step/dt + 0.5). With 1/31 kept at 60 fps that count becomes 2 instead of 1; with 0.016 it stays 1.
4. 0x824c3984 = 4 is a render or material setting (fn_81a39942), not timing.
5. Added: a flip handshake. In fn_81aa9320, after each sceGxmDisplayQueueAddEntry the submitting thread clears an event flag, signals the semaphore at +0x28cdc and waits on the event flag. The display callback fn_81aa9412 sets that flag only after sceDisplaySetFrameBuf(…,1) plus one sceDisplayWaitVblankStart. So each submit waits until the previous frame has flipped. There is no 30 fps cap there, but every frame of the render thread's work has to fit in 16.7 ms.

What a 60 fps mode must change for this game:
(a) Write singleton+0xcc = 60. The simplest way is IHOOKS "0x8178c5f2:frames30": hooks.c doubles r1 after the movs, so 30 becomes 60, but only if frame_rate is 60 at startup. For a live switch, a game hook should write 60 or 30 to *(*0x82474314 + 0xcc) each frame, for example at the entry of fn_81a7756c.
(b) In the same place, set 0x82474334 back to 0.016 at 60 fps, and to 1/31 (0x3d042108) at 30. frame_dt cannot do this because it only replaces 0x3d088889.
(c) Optionally write 1/60 to *0x82494030's float at 60 fps, to match the constructor default. No reader was found, so this is low priority.
(d) No frame_dt IHOOKs are needed for the reviewed 1/30 sites. Game time comes from vblanks measured with sceDisplayGetRefreshRate (59.94). The fixed users of fps_target (1/fps steps in fn_81a301c0, fn_81a30224, fn_81a30474, fn_81a4e58a, fn_82099194; the 1/fps cap in fn_82092d00; the 1e6/fps divide in fn_81aa38e0) follow the new value on their own.
(e) The runtime's frame_rate setting does nothing for this game today. It only changes sceDisplayWaitSetFrameBufMulti, which the game does not import, and display_frame_dt is only reached through IHOOKs.
(f) The real blocker is outside pacing: the 11-13 ms per frame render-target sync ("picture copy", docs/psnova/frame-rate.md). Aska runs it while holding the renderer lock, and the render thread's per-frame vblank handshake has to fit in 16.7 ms. Until that cost is gone, setting fps_target to 60 will give at best the current about 25 fps with smaller steps.
(g) Risk: the callback ignores notifyCount, so if the host VSync thread wakes more than one vblank late, the game's counter falls behind the vblank clock. The runtime sends the full missed count as notifyCount, but the game adds only 1.

## timestep

**Summary.** I re-checked every finding against the disassembly (the scratchpad vdis/xref/eaxref helpers over analysis\eboot.data.json), the recompiler and the runtime. Everything was read-only: no edits, builds, runs or git commands.

Most of the timestep report holds. The game is variable-step. A VSync thread's vblank callback adds 1 to 0x8249d100. The frame wait fn 0x81a24692 sleeps until last + 60/T->fps, then records the measured vblank count, 1/count and seconds in T = *0x82474314. Application.cpp's loop steps the game by min(g_dt × 60, 3.0). The only 30 fps cap in game code is `movs r1,#0x1e` at 0x8178c5f2 followed by `str.w r1,[r0,#0xcc]` in fn 0x8178c3e4, which runs once at boot.

Corrections and additions:
1. The wait's interval is its r1 argument when that is non-zero, and 60/fps only when r1 is 0. The fields are per slot (slot index in r2), and the frame end uses slot 0. With r3=1, the wait wakes one vblank early, queues render command 0xa (fn 0x81a72074 -> 0x81a8ff10), then waits the last vblank.
2. T+0xc8 is the game's slow-motion scale. It is written as 1.0 at 0x812fbebc and 0.3 at 0x812fc10a.
3. g_vblanks at 0x8249c25c has no reader. g_dt at 0x8249c258 is read only by fn 0x81aed6ee.
4. The 1/31 cloth/physics update is not simply "one step at 60 fps". It derives an iteration count and a step from dt, and at 60 fps it takes a different branch.
5. Pad key-repeat (fn 0x81b19e9a) counts once per vblank. The input thread (fn 0x81a1f276) polls every 8 ms, so key-repeat does not depend on frame rate.
6. The frames30 IHOOK is not in packs\PCSG00351\pack.toml today. IHOOKs are emitted when the C is generated, so adding it needs a regeneration.
7. MOST IMPORTANT (missed): the runtime's picture path holds each flip for 2 vblanks. The game's flip callback fn 0x81aa9412 calls sceDisplaySetFrameBuf(fb, 1) and then sceDisplayWaitVblankStart. In runtime\gfx\display.c, h_set_frame_buf (line 192, present-at-vblank, on whenever a window is open) first sleeps to vb_now()+1, then runs gfx_present. After that, h_wait_vblank (line 287) waits for vb_now()+1 again, which is the edge after. Each flip therefore takes at least 2 edges, which caps presentation at 30 Hz whatever T->fps is. If gfx_present (the picture copy) takes longer than one vblank, the flip takes 3 edges. That fits the roughly 25 fps the game runs at now. On the console, SetFrameBuf(NEXTFRAME) followed by WaitVblankStart costs 1 edge.

What a 60 fps mode must change:
(a) Make T->fps 60. Add `0x8178c5f2:frames30` to this pack's IHOOKS. recomp.py passes reg=r1, so 30 becomes 60 before the store. Regenerate the C and have frame_rate=60 set at launch. For a live toggle instead, use a per-frame hook that rewrites T+0xcc. A hook only on the wait at 0x81a246be is not enough, because the 'fixed'-mode animation code reads 1/T->fps.
(b) Make the runtime flip take 1 vblank for this game. Either make a WaitVblankStart that follows SetFrameBuf on the same thread return at the edge the present already slept to, or turn present-at-vblank off for this title. Keep gfx_present well under 16.7 ms.
(c) Add no frame_dt IHOOKs for the main simulation, and do not paste hookscan's IHOOKS line. 0x81365eb6 would break if hooked.
(d) Settle these with 30-vs-60 watch counts: the fade setup at 0x8186ec1c/0x81fcc168, the 1/60 effect cluster, cloth at 0x81ad46c4, and the caller-supplied dt mode ([obj+0xc4] -> [obj+0xa8]) in the animation players.

Minor: the runtime's vblank grid is 60.00 Hz, but the game divides by the 59.94 that sceDisplayGetRefreshRate returns, so game time runs about 0.1% fast. This is harmless.

- **0x81aa9412 (flip callback, called on libgxm's display-queue thread; queued by sceGxmDisplayQueueAddEntry at 0x81aa9392) + runtime/gfx/display.c h_set_frame_buf line 192 and h_wait_vblank line 287** (runtime 30 Hz present cap (NEW, blocks 60 fps), high): The game flips with sceDisplaySetFrameBuf(fb, 1=next frame) and then sceDisplayWaitVblankStart. Data addresses shift by `ADDR_DATA_DELTA` (`0x1714000`), not by the code delta: the vsync singleton `0x82474314` is

**The key-repeat gate is vblank-counted, confirmed at instruction level.** `fn_83219e9a` reads the vsync singleton,
calls `fn_83124788` for the vblank counter (`0x83219eae: bl #0x83124788`), and compares it with the cached copy at
`[this+0xc8]` (`0x83219ec0: cmp lr, r0`). It advances its delay and interval timers only when the counter changed. The
gate therefore ticks once per vblank: 60 a second on the console's grid and 120 a second at 120 Hz. The repeat delay is
half as long at 120 fps, so the reported menu-repeat defect is a factor of two and not four.

**Grid rate is frame rate, which is why 120 fps moves every counter.** The limiter waits `uidiv(60, T+0xcc)` vblanks and
the pack hook writes 60, so a frame is one vblank and the grid rate *is* the frame rate. A 60 Hz grid therefore cannot
exceed 60 fps, and the flip handshake (SetFrameBuf plus one WaitVblankStart) puts its own one-edge floor under it. So
120 fps needs a 120 Hz grid, and at 120 Hz every engine timer that counts vblanks ticks at twice the console rate while
every timer that counts frames ticks at four times the console's 30. Time-based logic is unaffected: the game's clock
reads 1/120 s per frame at that grid and `speed` reads 1.00x.
