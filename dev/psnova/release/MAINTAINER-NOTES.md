# Maintainer notes: Phantasy Star Nova Recomp, Windows release 0.1.0 Beta 1

These notes are for whoever builds and shares the release. They are not for players. The player-facing instructions are in [README.md](README.md). Delete this file from the download if you do not want to share it.

## Before you share this folder

1. **The font.** The release ships no font and names none: Setup asks the player for any `.ttf` or `.otf` (README step 1, the Font field), takes whatever they choose, and says when it cannot open it. Nothing to remove and no licence to check.
2. Make sure there is **no `NovaData` folder** next to `setup.py`. It holds the builder's own game data, saves and settings. A clean release has none.
3. Zip the folder so it extracts to a single folder. `engine\release\ffmpeg-6.1.1.tar.xz` and the other FFmpeg notices must stay in the download: the bundled FFmpeg executable is GPLv3.

### Changes made to the engine for this release

The release engine matches the development tree for the UI, input, graphics, overlay and audio code. These files differ on purpose:

- `runtime\core\player_paths.h` (new), `io.c`, `fios.c`, `apputil.c`, `ui\save_backups.c`: guest saves, save backups and deleted saves are kept under `RECOMP_SAVE_ROOT`, so they sit outside the replaceable build. `fios.c` now uses the same path resolution as `io.c`.
- `packs\PCSG00351\hooks.c` and `pack.toml`: the Arabic right-alignment hooks are removed. The two extra function seeds are added.
- `pipeline\vitarecomp.py`: a plain (unencrypted) update with its own ELF no longer needs the base game's license, and a native ELF dump that kept the `eboot.bin` name is accepted.
- `decrypt\vitadecrypt\pkg.py` (PKG import, 25 November 2026): `extract_pkg` used to read the whole PKG into memory (about 3.3 GB for Nova) and then hold a decrypted copy of each file. It now checks the file table first and streams each file in 8 MiB chunks. `inspect_pkg` reads a PKG's identity and file table from a forward-only stream, which is how setup looks inside a ZIP. Before anything is written, every entry must lie inside the file, every name must be safe on Windows (no `..`, absolute or drive paths, `:` or other forbidden characters, reserved device names such as `CON`, trailing dots or spaces), no two names may differ only by case, and no file may sit inside a name that is also a file. Self-test: `python -B -m vitadecrypt.pkg --selftest` from `engine\decrypt`.
- `decrypt\vitadecrypt\game.py`: the PKG's outer layer is extracted to a `.add-pkg-*` folder beside the output folder instead of the system temp folder, so gigabytes of scratch stay on the release drive and one pattern (`.add*`) names everything an interrupted import can leave.
- A dev-checkout patch for the two files above is `Nova PKG QA\evidence\engine-decrypt-changes.patch`. The development checkout was not changed.
- The `Play Nova.exe` launcher (`engine\release\play_nova.c`) sets `RECOMP_SETTINGS`, so the game reads and writes only `NovaData\Player\settings.ini` and never touches `%APPDATA%\ProjectNativ`.
- The launcher also records every start, launch failure and exit in `NovaData\Player\launch.json` (the one before it in `launch.prev.json`; no paths in either). After a launch failure or an abnormal exit (any exit code but 0, including a Windows exception code) it offers to create a support report (it runs `Setup Phantasy Star Nova.exe --export-report`). After a normal quit it starts a hidden, throttled update check. A short wait covers a Setup that is switching builds and holds the game lock. `NOVA_LAUNCHER_QUIET=1` turns off its dialogs and the background check, for test scripts that kill the game.

### Default settings

On first setup, `NovaData\Player\settings.ini` is created once with: `input_mode = auto`, `render_scale = 4`, `frame_rate = 60`, `sharpen = 0.507067`, `fullscreen = 0`. Setup never overwrites an existing file. The 4× scale and the 60 FPS target are what the 22 November 60 FPS investigation ran with on an RTX 5060 Ti (`docs/psnova/fps-investigation-2026-11-22.md`). I could not trace where the sharpen value 0.507067 (51%) came from. The code default is 0.35 and the development library's own settings files do not set it, so decide whether to keep it. **4× is heavy for weaker GPUs.** To ship a gentler default, change `render_scale` in `setup.py` (search for `render_scale = 4`) to 2. The pack's rendering fixes (sRGB, deferred draws, depth clip) are compiled in through `RUN_ENV` in `pack.toml`.

## How setup works

1. **It reads the inputs** (`setup_sources.py`), and nothing is written except `NovaData\setup-inputs.json`, which remembers the selected paths so the window can reopen them. The player gives a base PKG and an update PKG, or one ZIP with both (CLI: `--game`, `--update`, and `--license` for the game's `work.bin` or `.rif`); extracted folders, and a PKG mixed with a folder, still work from the CLI.
   - A **PKG** is identified from its header, its embedded `param.sfo` and its (unencrypted-key) file table, with no license. The file table is checked as well: offsets, Windows-safe names. A **ZIP** member is recognized by the `\x7fPKG` magic, not its name, and read forward-only for the same header. Directories, other files, add-on (DLC) PKGs and other titles' PKGs inside a ZIP are skipped, with a note.
   - The roles come from the headers, not the field or the file name: `PCSG00351`, content ID `JP0177-PCSG00351_00-NOVAAPPLICATION0`, **one app package with category `gd` and version `1.00`** and **one patch package with category `gp` and version `1.05`**. A file the player chose directly must be a usable package, or setup stops and names it. A problem with something found *inside a ZIP* matters only if it leaves a role empty: a ZIP with update 1.04 and 1.05 uses the 1.05 and notes the 1.04; a damaged DLC PKG in the ZIP is noted and skipped. A role matched twice (two base PKGs, or the ZIP and the Update field both holding a 1.05) is an error that names every file and ZIP member.
   - A base PKG without a license inside needs `--license`. The license must be 512 bytes (or NoNpDrm's 1024) and carry Nova's content ID. A PSN-account license is accepted with a warning (the pipeline only keeps NoNpDrm-kind licenses, and a real wrong key stops the import with a clear message). The embedded work.bin of a PKG is detected in its file table.
   - Folders keep the checks they always had: `param.sfo` identity, the archives, `eboot.bin`, the `sce_pfs` files, the license size, the `disc1` and `sce_module` files.
   - Then it checks the SHA-256 of `PSVUPDAT.PUP` (3.74) and the font. Each failure names the file or version it expected.
2. It computes **three fingerprints and the build ID they make together**. The *inputs* part is the SHA-256 of every file in an extracted folder input, **of each package's own bytes (a PKG, or a PKG inside a ZIP after unzipping, so the same PKG gives the same ID loose or zipped)**, and of the license's 512 bytes. The *native* ID covers `version.txt`, the firmware, **every file under `engine\decrypt`, `dev`, `packs`, `pipeline`, `recompiler`, `runtime` and `third_party`** and the inputs. The *text* ID covers `build_text.py` and `localization\text`, the font, Windows' Segoe UI Bold (the text builder's fallback font) and the inputs. The *movies* ID covers `build_movies.py` and `localization\movies`, the font, `ffmpeg.exe`, **the CPK reader and writer under `engine\pipeline\cri`** (`build_movies.py` imports `cpk.py` and `cpk_merge.py` from there, so an engine update that changes them rebuilds the movies) and the inputs. The build ID (`NovaData\installs\<24 hex>`) is the SHA-256 of the three. A changed input is a new build. Reading a ZIP member to hash it also finds a damaged ZIP (bad CRC) before anything is built. The toolchain and Python are pinned by `version.txt`: bump it when you change them. The sources are the active build's own (a staged update component, while it is newer than the release folder's files and still hashes to its recorded value) or the release folder's.
3. It runs the stages: firmware, base, update, import, analyze, recompile, build, English text, English movies. After each stage it checks the outputs and records it in `progress.json`. The recompile stage also verifies the generated labels, and the import stage verifies the layered `libc` and `disc1` files by hash. A rerun skips finished stages and redoes a stage whose output is missing.
   - **Base and update stages with packages.** Each starts by deleting the scratch an earlier, interrupted import can leave (`NovaData\scratch` and every `.add*` folder in the build's library). A ZIP member is then streamed to `NovaData\scratch\imports\base.pkg` (or `update.pkg`), hashed while it is written and compared with the hash taken for the build ID (a ZIP that changed in between is refused), imported with `vitarecomp add <file> --license <license> --no-build`, and deleted. A PKG chosen directly is read where it is. The same SHA-256 checks as for folders (`BASE_FILES`, `PATCH_FILES`) run on the result before the next stage, with wording that blames the package. A failed import shows its last log line first and says when the license did not decrypt the package.
   - **Reusing an earlier build.** Before the stages run, setup looks for an earlier build whose `provenance.json` has the same *native* ID and whose recorded output files (firmware, native and, for each English archive whose ID also matches, that archive) still have their recorded SHA-256, and whose `app0`, `patch0` and layered files still match the fixed hash tables. If it finds one, it copies that build's library into the new build as files of their own (the donor's hard links between `app0` and `fs\app0` are kept as links inside the copy, so a 3 GB archive stays one file; nothing is linked to the donor), leaves out the generated C sources, objects and captures, and marks the stages it reused in `progress.json`. Only the stages whose fingerprints differ run. If nothing matches, or a record is missing or invalid, it makes the build the long way. Builds made before this feature have no record, so the first successful run of this setup builds in full and writes the record.
4. It writes `language.txt` and `default.txt`, creates `NovaData\Player` once, copies `Play Nova.exe` to `Phantasy Star Nova.exe`, writes the build's `provenance.json` (release, version, the fingerprints, where each component's files came from, the SHA-256 of every file that makes it run, its size), takes the game lock (the launcher holds `NovaData\Player\playing.lock` while the game runs: if it is held, the new build stays complete and unselected until setup is run again), checks the build could start, and **then** switches: `previous.txt` takes the old `current.txt`, and `current.txt` is replaced in one atomic step. Every build except those two is deleted (locked files are retried at the next run), and staged update components no kept build uses are deleted. The build setup is recording is also in `NovaData\setup-attempt.json` from the first step.
5. The original game files, firmware and font are only read. Saves, backups, screenshots, logs and settings live in `NovaData\Player` and are never touched by setup.

The setup process holds `NovaData\setup.lock`, so two copies cannot run at once. The install needs about 14 GB free and takes a while: the recompile and Windows build use every core.

## Support reports

`Export support report` (the window), `--export-report` (a console) and the launcher's dialog all call `setup_reports.export_report`. It writes `NovaData\Reports\support-<local time>.zip` from an **explicit list**: `summary.txt`, `summary.json`, `setup\attempt.txt`, `setup\logs\*.log` (head and tail of each log of the build setup was making, at most 20), `game\session.log` and `game\session.prev.log` (head and tail, bounded), and only these fields: the release and build IDs, the graphics and input settings named in `SETTINGS_ALLOWLIST`, the fields of the attempt and launch records named in `ATTEMPT_FIELDS` and `LAUNCH_FIELDS`, the update state fields in `UPDATE_FIELDS`, the Windows version, and the game's `gpu:` lines. **Never exported:** `setup-inputs.json`, saves and their backups, `captures`, `guest-input*.txt`, the other settings, `licenses`, fonts, `scratch`, packages, memory dumps, and the attempt's `private_names` list.

Every member passes the redactor first. Paths inside the release folder keep their relative part (`<NovaData>\installs\<id>\logs\build.log`); a path under the user's home, temp or app data folders is replaced together with everything under it by `<home>` or `<path>`; any other drive or network path becomes `<path>`; the user and computer names become `<user>`; the names of the files the player selected (including ZIP members) become `<source-file>`, and the **exact paths** the player selected (recorded in the attempt as `private_paths`) are replaced as whole strings **first**, so the words after one survive ("The base package <source-file> produced a eboot.bin.elf that differs ..."); `key=value` pairs whose key names a license, password, token or secret, bearer tokens and 32-digit hex values (a klicensee) are replaced. Any *other* absolute path (a path with spaces has no safe end) is replaced together with the rest of its line, which can cut a message short: the first version of the redactor did this to every selected file too, and a failed build's report lost the cause (found while reading the real reports, fixed, and tested by `test_reports.py`). A second pass then **scans the result and refuses to write the ZIP** if a drive path, the user or computer name, a selected file name or a 32-digit hex value is still there.

The summary labels the latest game session **Normal quit**, **Crash** (the log holds the runtime's `== crash:` line, or the exit code is a Windows exception code, 0xC0000000 or above), **Abnormal exit (code N)**, **Launch failure**, or **Interrupted or incomplete** (no exit recorded). It labels the latest setup attempt **Succeeded**, **Failed at stage '...'**, **In progress** or **Interrupted or incomplete** (no outcome recorded and the process is gone). It states the active build (and whether it can start) separately from the attempt, so a failed update names the build the player can still play.

## Updates

**Configuration.** `engine\release\update.json` is pinned in the release: `enabled`, `channel`, `feed_url` (https), `public_key` (64 hex digits, Ed25519). **The shareable build ships with `"enabled": false`.** Setup then shows "Update checks are off in this release" and never touches the network. To turn updates on for a release, set a production HTTPS feed and the production public key, and nothing else. A loopback `http://127.0.0.1` feed is accepted only with `"allow_loopback_http": true`, and the test hook `NOVA_QA_FREE_BYTES` only with `"qa": true`: those two keys are for QA copies, which must never be the shared build (`Nova Diagnostics and Update QA\scripts\make_test_release.py` makes such a copy).

**Keys.** Make a key pair once, keep the private half off this folder and off any shared drive, and put the public half in `update.json`:

```powershell
engine\python\python.exe -B engine\release\publish_update_feed.py keygen --private C:\keys\nova-update.key --public C:\keys\nova-update.pub
```

**What an update contains.** Three components, each a ZIP of whole files: `engine` (the folders `decrypt`, `dev`, `packs`, `pipeline`, `recompiler`, `runtime`, `third_party`), `text` (`build_text.py` and `text\`) and `movies` (`build_movies.py` and `movies\`). Nothing else can be updated: not `setup*.py`, the root launchers, `engine\release`, the verifier, `version.txt`, the bundled Python or the toolchain. Those need a new release download (raise `min_updater` for anything that needs a newer Setup).

**Publishing a release.** Prepare a source tree with the changed files (a copy of `engine` and `localization` is enough), then publish all three components every time; clients download only the ones whose content hash differs from what they have:

```powershell
engine\python\python.exe -B engine\release\publish_update_feed.py publish --private C:\keys\nova-update.key --out C:\feed `
    --release 7 --version 0.1.1 --notes-file notes.txt --engine-root D:\src\r7\engine --localization-root D:\src\r7\localization
engine\python\python.exe -B engine\release\publish_update_feed.py verify --public C:\keys\nova-update.pub --feed C:\feed
```

The release number must only ever go up. The output is `C:\feed\stable\manifest.json`, `manifest.sig` (hex Ed25519 over `nova-update-manifest-v1\n` plus the manifest bytes), and `payloads\<kind>-<content>.zip`. Any static HTTPS host serves it; keep old payloads. Do not edit `manifest.json` after signing (the signature covers its exact bytes).

**What Setup does.** *Check* (Setup when it opens, the launcher after a normal exit, or the button): at most once a day across all of them (`NovaData\Updates\state.json`, with a lock so two entry points never ask at once), unless forced. It fetches the manifest and signature, verifies them with the pinned key, and ignores a release number not above the highest this install ever accepted (`highest_release`, which only goes up and is not lowered by a rollback) or above `min_updater`. It stores the plan: version, notes, download size, and `full` (engine), `english-text`, `english-movies`, or a combination. *Install update* (button or `--install-update`): re-verifies the stored manifest, requires the game closed (it holds the game lock for the whole install), checks free space (the download plus the active build's size plus 1.5 GB) and, if English text or movies must be rebuilt, the font and tools, **before downloading anything**. It downloads only the changed components, checks each payload's size and SHA-256 against the signed manifest before unpacking, unpacks into `NovaData\Updates\components\<kind>\<content>` (only plain files inside that component's folders, Windows-safe names, no links; the unpacked tree must hash to the manifest's content hash), and builds a new generation from those sources. An engine update has no need of the original packages or the firmware: it copies the prepared game and firmware from the active build and runs import, analyze, recompile and build. A text or movies update copies the whole active build, keeps the native files and the other English archive, and rebuilds only its own archive from the original Japanese CPKs. The movie builder runs without Python's isolated mode and with the active engine's `pipeline\cri` folder on its import path, because a movies component unpacked under `NovaData\Updates` has no `engine` folder beside it (found when the first movie update failed with `No module named 'cpk'`). When the new build is complete and `launchable`, setup switches `current.txt` atomically, records the release as accepted and keeps the old build as `previous`.

**Rolling back.** The window's **Roll back** button, or `Setup Phantasy Star Nova.exe --rollback`, with the game closed, swaps `current.txt` and `previous.txt` (it refuses if the earlier build is gone or cannot start). Rolling back again goes forward. The saves and settings are never part of a build. Rolling back does not lower `highest_release`, so the feed's older payloads stay ineligible.

**If an update fails.** Nothing changes until the switch: a failed or killed update leaves the active build and the player's files alone, and the half-built generation is reused by the retry (the stage journal skips finished stages). The support report of that machine names the failed attempt and the build still playable. A build made before records were kept has nothing to reuse: the message tells the player to run **Build and install** once.

**Engine updates and the original packages.** A change to `engine\decrypt` does not re-decrypt the player's packages in an update (the prepared game is reused). Ship such a change as a new release download.

## How the release folder was built

1. Copy the engine from the development checkout at commit `5d30e61` plus its working-tree edits into `engine\`. Apply the changes listed above. Add `localization\`: the English recipes exported from `dev\psnova` and `dump\psnova-l10n` (English only, no Arabic) by `export_text.py`, which lives in `.nova-text-verification` beside the development checkout and is not part of the release, plus the build scripts `build_text.py` and `build_movies.py`.
2. Compile the two launchers from `engine\` with the bundled Clang:

   ```powershell
   & toolchain/llvm-mingw/bin/x86_64-w64-mingw32-clang.exe -O2 -Wall -Wextra -Werror -mwindows -municode -static release/play_nova.c -o "release/Play Nova.exe"
   & toolchain/llvm-mingw/bin/x86_64-w64-mingw32-clang.exe -O2 -Wall -Wextra -Werror -mwindows -municode -static release/setup_launcher.c -o "../Setup Phantasy Star Nova.exe"
   ```

   Both commands compile without warnings, and the output is the same size as the shipped files. The bytes differ because the PE header carries a build timestamp, so the shipped binaries are the ones that were tested. `play_nova.c` and `setup_launcher.c` changed for the support reports and updates (launch records, the export offer, the background check, the windowless export): recompile both after editing them.
3. Run `powershell -ExecutionPolicy Bypass -File engine\release\prune_release.ps1`. It removes Python's docs, test suite, pip and build files, the Arm and i686 compiler targets, and the compiler's debugger and linter. This takes the folder from about 1.2 GB to about 760 MB. Run the clean-folder test **after** pruning.
4. Never run `engine\python\python.exe` in the release folder without `-B`: it writes `.pyc` files. The prune script removes them.
5. Remove the font (see above), then zip.

To update the release: copy the new engine files over, rebuild the launchers if their sources changed, prune, and test again from a fresh folder. Players extract over the old folder and run setup. Changed engine or localization files rebuild automatically.

## What was verified

All checks ran on 24 November 2026 on the development PC (Windows 11 Pro, Ryzen 7 5700X, 48 GB RAM, NVIDIA GPU). Nothing from the development checkout was used. The test folder was a copy of this release, **pruned as it ships**, at `...\Nova Final QA\Nova Rélease Test`: a path with spaces and an accented character, next to but outside the checkout. The inputs were the player-style ones: the extracted Japanese base 1.00 and update 1.05 (an encrypted dump with `sce_pfs` and `work.bin`, laid out as `app\PCSG00351` and `patch\PCSG00351`, with the fan `rePatch` folder alongside it, which setup ignores), the official `PSVUPDAT.PUP`, and the bundled font. The test scripts are in `Nova Final QA\scripts` beside the checkout. They are not part of the release.

**Clean install, through `Setup Phantasy Star Nova.exe`**
- One command-line run took every stage to the end and produced `Phantasy Star Nova.exe`: about 33 minutes, including a deliberate interruption, with other builds and tests running at the same time. The build folder is 9.7 GB, and the release itself is 766 MB. The 14 GB figure in the README is that plus headroom.
- **Interruption.** The setup process was killed hard during the analyze stage. No process was left running. A second run reported the four finished stages as already complete and resumed at analyze.
- **Repeat run.** Running setup again on the finished install took 10 seconds. All nine stages were skipped, the scratch movie files were deleted, and `NovaData\Player` was byte-identical afterwards (a planted save and a customized `settings.ini` were checked by SHA-256). The same run through the setup window's **Build and install** button gave the same result.
- **Independence.** The built `game_host.exe` contains no path from the development checkout. Only the build folder's own `__FILE__` strings. An earlier full run of the same release in a second folder (with the font chosen from outside the release, and before the last few `setup.py` fixes) produced identical generated code (all 121 `.c` and `.img` files, apart from `entry.txt`, which setup writes last), an identical English text archive and an identical English movie archive.
- **Validation messages**, re-run against the final `setup.py`. Game inputs: no game folder, a missing update, an update that reports 1.04, an update that belongs to another title, missing archives and `disc1`/`libc` files, and a firmware file that is not the supported one. Each stops with a message that names the file or version. Font: none in the release and none chosen, a chosen path that does not exist, and a file that is not a font. All 10 pass, and none writes anything to disk. The 1.04 and wrong-title cases use a copy of a fixture `param.sfo` that is edited on the fly.
- `remove_superseded_installs` is unit-tested: it removes old builds (read-only files included), reports a build it cannot delete and removes it on the next pass, and never touches the current build, saves, settings or unrelated names.

**English localization**
- Text archive: 804,933,368 bytes, SHA-256 `760c458e2137407d5c20feb4a3da37f51b5aa1d17b92736127b55011f5d4fc4b`, 27,817 entries. Compared entry by entry with the English archive that the development library uses today, every entry is byte-identical except the two listed under Known limits.
- Movie archive: 430,478,568 bytes, SHA-256 `c5452b81eebc23de32f96023e62aee71c37f8491099a21205aa179d8a1b03567`. All 21 entries read back. The 11 movies that are not subtitled are byte-identical to the originals. The 10 rebuilt ones have the recipe's frame counts at 960 × 544 and an audio stream whose SHA-256 equals the original's. ## Known limits

- **Font license.** See the first section.
- **Text source.** The English message text began as the fan rePatch wording and was revised afterwards (`localization\text\messages.json`). Check its redistribution status before you share it widely.
- **Coverage.** Some menus, lines and screens still use the original Japanese. This is the state of the localization, not a defect of the installer.
- **Seven story movies differ from the dev library's installed archive** in the position of the subtitle backing bar only. See "What was verified". The bar's size and position come from the renderer in `localization\movies\subtitles.py`.
- **Two entries differ from the 21 November English archive in the dev library.** `msg_10323.rmd` (the "Lv." label, which the dev archive re-draws in the English font) and `msg_100010050005000.rmd` (an unused developer placeholder) are in that archive but not in the build. The current builder rule skips rows whose English equals the Japanese apart from spacing, and both rows are of that kind. Every other entry is identical.
- **New text not yet seen in the game.** The 40 messages added on 24 November are verified in the archive only. See "Localization pass" above for what remains to check.
- **Controllers.** The controller path was exercised with SDL virtual gamepads built into a test-only runtime variant, not with physical hardware.
- **Defender and SmartScreen.** The built `game_host.exe` is compiled on the player's PC and unsigned.
- **Update PKGs.** No genuine 1.05 update PKG has been through setup. The update-PKG and ZIP paths ran on a PKG repackaged from the extracted 1.05 files and on fixtures. If a real update PKG fails on a field the repackaged one does not exercise (a different `info` table, a name the Windows checks reject, a license inside it), the message names the package and the first thing to look at is `vitadecrypt.pkg.inspect_pkg_file` on it.
- **Failed attempts leave their build folder.** A setup that stops with inputs that name a different build (another license, another package) leaves `NovaData\installs\<id>`, with its firmware and, after a stop in a later stage, its imported game (up to about 6 GB). Only a *finished* setup deletes superseded builds. This was already so for folder inputs.
- **Free space.** The 14 GB check runs before the first stage of a build and stops setup at 13 GB free. Setup with a ZIP also holds the unpacked base PKG (3.3 GB) while it is imported. The check does not count that separately: the 14 GB figure covers it with about 4 GB to spare for the real game.
- **Update trust is one key.** `update.json` pins one Ed25519 public key. An engine update replaces the recompiler, the runtime and the build scripts that Setup then runs on the player's PC, so whoever holds the private key controls those PCs. There is no rotation or revocation: a new key needs a new release download. Keep the private key offline and test a feed with `publish_update_feed.py verify` before uploading it.
- **Only a QA copy may point at a loopback feed.** `allow_loopback_http` and `qa` exist for the test copies made by `make_test_release.py`. The shareable build ships `"enabled": false`. A production feed was never tested: the https path, certificate handling and a real host's behavior are unverified.
- **Updates are not a downgrade barrier against the local user.** `highest_release` lives in `NovaData\Updates\state.json`; deleting it forgets the highest accepted release. It protects against a stale or replayed feed, not against the player.
- **Update space.** An update builds a second library next to the working one: Setup asks for the download plus the active build's size plus 1.5 GB (about 8 GB on this PC) and checks before it downloads. Only the active and previous builds are kept, and a *finished* setup or update deletes the rest.
- **Reports cut some lines.** A path that is not one the player selected (and not under the release folder) is replaced together with the rest of its line, because a Windows path with spaces has no safe end. A message that names such a path loses the words after it; the setup log excerpt usually repeats the cause. Selected files are exempt (their exact paths are replaced as whole strings).
- **Real crashes.** The "Crash" label rests on the runtime's `== crash:` log line or a Windows exception exit code. It was tested with a stand-in game; no real crash of the real game was captured.
